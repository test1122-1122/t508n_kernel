# T508N 无串口验证指南

> 没有 UART 线也能完整验证 Linux 内核启动。本机有两条现成的无串口日志通道
> （都来自上一轮逆向成果）+ A/B 双槽保护，验证闭环如下。

> ⚠️ **重要警告**：`vendor_boot_linux.img` 内的 mainline DTB **只能配 mainline 内核**。
> 官方 5.4 内核 + mainline DTB = 必然无限重启。**永远不要把它刷到存有官方系统的槽位**
> （默认安全网是 b 槽）。若已误刷导致 b 槽循环重启，用 `restore_stock.bat` 恢复。

## 0. 核心思路：用 A/B 双槽做"安全网"

- **boot_a / vendor_boot_a**：刷我们的 `boot_linux.img` + `vendor_boot_linux.img`（试验槽）
- **boot_b / vendor_boot_b**：保持官方系统不动（安全网，内含 Magisk root）
- 试验槽起不来 → 强按电源 ~10s 重启 → `fastboot set_active b` → 回到官方 Android
  → 用 **adb**（官方系统有 Magisk root）把日志全部拉出来分析 → 迭代后再刷 a 槽。

## 1. 通道一：uboot_log 分区（看引导器侧）

LK 每次启动都会把带 [ms][cpu] 时间戳的日志写进 `uboot_log` 分区，**跨重启保留**。
回到官方系统后：

```bash
adb shell su -c "dd if=/dev/block/by-name/uboot_log of=/sdcard/uboot_log.img"
adb pull /sdcard/uboot_log.img
```

在电脑上（本仓库工作区即可）：
```bash
strings uboot_log.img | grep -E 'Booting slot|kernel|ramdisk|vbmeta|start_linux|verify'
```

**判定**：
| uboot_log 里看到 | 含义 |
|---|---|
| `Booting slot_a` + `start linux at PC:0x80080000` | LK 已把我们的内核/DTB/ramdisk 正常加载并跳转 ✓ |
| `boot_a: Public key ... does not match` / `verify_ret` 非 0 | 镜像校验问题（解锁态会被容忍，注意 `verifiedbootstate`） |
| 停在 `read OK` 之前 | 镜像格式有问题（用本仓库工具检查布局） |

## 2. 通道二：pstore/ramoops（看内核侧，★主力通道）

已在 `tools/dts/ums9620-ot5.dts` 中加入与官方相同位置的 ramoops（0xfff80000），
内核配置已开 `PSTORE_RAM + PSTORE_CONSOLE + PSTORE_PMSG`（console 会把**全部内核日志
和我们 init 的 echo 输出**存进去，重启不丢）。回到官方系统后：

```bash
adb shell su -c "ls -la /sys/fs/pstore/"
adb shell su -c "cp -r /sys/fs/pstore /sdcard/pstore"
adb pull /sdcard/pstore
```

**判定矩阵**：
| pstore 内容 | 结论 | 下一步 |
|---|---|---|
| `console-ramoops-0` 里有完整启动日志，末尾有 `=== T508N Linux boot OK ===` | **内核+init 全通**，只是没显示/没控制台 | 进入驱动点亮阶段 |
| 有内核日志但卡在某处（如 clock/pinctrl probe 失败） | 内核早期问题，按日志迭代 | 把日志发回分析 |
| pstore 里什么都没有 | 内核死在 ramoops 注册之前（极早期：GIC/timer/内存问题），或根本没被 LK 加载 | 结合 uboot_log 判断；调整 DTS/保留区 |
| 官方系统的 `/sys/fs/pstore` 里有 `dmesg-ramoops`（官方内核自己的崩溃记录） | 说明官方内核也用过这块区域，机制本身有效 | — |

## 3. 通道三（推荐追加）：init 把日志也写进 pmsg

initramfs 的 `/init` 已支持 `pstore pmsg`：官方系统里 `cat /sys/fs/pstore/pmsg-ramoops-0`
可看到我们 init 通过 `/dev/pmsg0` 写入的用户态消息。若需要更细的用户态日志，可在
init 脚本里 `echo xxx > /dev/pmsg0`。

## 4. 其它无串口观察手段（按需）

- **USB gadget（终极方案，需补驱动）**：官方内核用 `musb_hdrc.ko`（MUSB 控制器），
  mainline 缺 Unisoc MUSB glue。移植后可用 USB 虚拟串口/网卡获得全功能 shell——这是
  "无 UART 全功能调试"的长期正解。
- **eMMC 标记**：mainline 有 `sdhci-sprd` 驱动（官方 DTS 就是 `sprd,sdhci-r11`），
  若 pinctrl/时钟沿用 LK 已初始化的状态能工作，init 可向某分区写标记文件，再回
  官方系统读取——作为"init 是否到达"的旁证。
- **屏幕/LED**：mainline 暂无显示驱动，LK 开机 logo 会保持显示，无法区分内核状态，
  不做依据。

## 4.5 实机测试结论与修复（uboot_log 判读）

**第二轮日志（uboot_log2.img）判读**：
- 我们的镜像仍被正确加载，但 `merge_dtbo : entry id is 0x2700, offset = 0x100 size=0x1d9eb`
  —— size=0x1d9eb 是 **stock DTBO（121KB）**，说明空操作 DTBO 没有生效
  （未刷入或未刷对槽），overlay 合并依旧失败。
- 注意：fastboot 刷 dtbo 后**无法直接读回验证**，验证手段就是下次日志里这行的
  size 值——应变为 ~0xd5（213 字节，我们的空 overlay）。

**第二轮修复补充**：`work/noop_dtbo.img` 已重做（含自签 vbmeta 页脚，8MB，
可直接刷 dtbo_a）。若下次日志 size 仍为 0x1d9eb，说明 dtbo_a 没有刷成功。

## 5. 一键验证流程（刷机侧）

**第一轮实机结果**（你们拉回的 uboot_log.img 分析）：
- LK 成功读取我们的镜像（kernel 46526976 / ramdisk 894530 ✓ 格式正确）
- 但 **stock DTBO overlay 合并进 mainline DTB 失败**：
  `fdt_overlay_apply(): FDT_ERR_NOTFOUND` → `image is not a fdt` →
  收尾阶段 `fdt_chosen_bootargs_append: FDT_ERR_BADMAGIC` → LK panic → 看门狗复位
  （**从未 start_linux**，内核一次都没被跳转）
- A/B 计数把 a 槽判死（tries 0）自动切到 b 槽 → b 槽 vendor_boot 也是 mainline DTB
  → 官方内核崩溃 → 这就是"b 槽无限重启"的来源

**第二轮修复（全部已产出）**：
1. `work/noop_dtbo.img` — 空操作 DTBO（board_id/sc-id 与 stock 一致但 overlay 为空，
   合并必然成功，不再破坏 DTB）← 核心修复
2. `boot_linux.img` / `vendor_boot_linux.img` — 已加自签 vbmeta 页脚
   （走"结果5 公钥不匹配"路径，解锁态下已被 Magisk 版 stock boot 验证可正常继续引导）
3. 内核开启 DEVMEM（STRICT_DEVMEM=n），为后续从 init 处理看门狗做准备

## 5. 一键验证流程（刷机侧）

```bash
# 0) 【先救回 Android】恢复 b 槽 vendor_boot（boot_b 仍是官方镜像）:
fastboot flash vendor_boot_b vendor_boot_b.img
fastboot reboot
#    → 此时应能回到官方 Android（A/B 会自动选 b, 因 a 已被判死）

# 1) 第二轮试验: 三件套刷入 a 槽
fastboot flash boot_a boot_linux.img
fastboot flash vendor_boot_a vendor_boot_linux.img
fastboot flash dtbo_a work/noop_dtbo.img     # ← 本轮新增, 关键
fastboot set_active a
#   (若 set_active 不支持: fastboot erase misc 后重启, LK 无 ABC 数据默认 boot a)
fastboot reboot

# 2) 若 ~2 分钟无反应（没显示驱动, 属正常, 不说明失败）:
#    强按电源重启进 bootloader, 回官方系统
fastboot set_active b
fastboot reboot

# 3) 官方系统里收集证据（上面 1、2 两条命令）
adb pull ...   # uboot_log.img + pstore/

# 4) 把两个文件发回, 我来判读并迭代内核/DTS
```
